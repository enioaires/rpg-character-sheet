## Project

**RPG Character Sheet**

Digital character sheet (in Brazilian Portuguese) for a homebrew tabletop RPG system — Berkana (mana), six-stage vitality, 14 attributes, 36 skills, spells/talents with level scaling, adventure kit, finances and notes. Used by the owner and their play group at the table to create, edit and track characters during sessions. Next.js app deployed on Vercel with a PostgreSQL database.

**Core Value:** Players can open their character during a session and edit any field inline with the change saved reliably — no lost edits, no wrong derived numbers.

### Constraints

- **Tech stack**: keep Next 16 / Hono / Prisma / TanStack Query / Bun — the fixes are refactors, not migrations.
- **Data compatibility**: existing rows in production must keep loading and saving; new Zod schemas must accept current data shapes (tolerate extra/optional fields).
- **Behavior**: derived numbers and UI behavior must stay identical after refactors.
- **Definition of done**: `npx tsc --noEmit`, `bun run lint`, `bun test` and `bun run build` pass.

## Conventions

## Naming Patterns

- React components use kebab-case filenames containing a PascalCase export: `components/character/basic-info-tab.tsx` exports `BasicInfoTab`, `components/character/quick-actions-bar.tsx` exports `QuickActionsBar`. The steering doc (`.kiro/steering/structure.md`) says PascalCase filenames, but the actual tracked files are kebab-case. Follow the kebab-case files.
- shadcn/ui primitives keep their lowercase kebab-case names: `components/ui/alert-dialog.tsx`, `components/ui/input-otp.tsx`.
- Hooks use the `use-` kebab-case prefix: `hooks/use-mobile.ts`.
- Lib modules are lowercase single words or kebab-case: `lib/api/queries.ts`, `lib/api/client.ts`, `lib/calculations/index.ts`, `lib/schemas/character.ts`, `lib/store/character.ts`, `lib/defaults/character.ts`, `lib/constants/character.ts`, `lib/db/index.ts`.
- Next.js route files follow the App Router convention: `app/character/[id]/page.tsx`, `app/characters/page.tsx`, `app/create/page.tsx`, `app/api/[[...route]]/route.ts`.
- Barrel files are named `index.ts` and re-export a folder: `components/character/index.ts`, `lib/calculations/index.ts`.
- Non-component type-only files are named `types.ts`: `components/character/types.ts`.
- camelCase for all functions and hooks: `calculateAttributeTotal` in `lib/calculations/index.ts`, `useCharacters` and `useCreateCharacter` in `lib/api/queries.ts`, `getDefaultCharacterData` in `lib/defaults/character.ts`.
- React hooks always start with `use`. Mutation hooks are named `use<Verb><Entity>`: `useUpdateCharacter`, `useLevelUpCharacter`, `useRecalculateCharacter`.
- React components are PascalCase and exported as named exports (`export function QuickActionsBar`), except page components, which use default exports (`export default function CharactersPage()` in `app/characters/page.tsx`).
- Event handlers inside components use the `handle` prefix: `handleCreateCharacter`, `handleViewCharacter`, `handleDeleteCharacter` in `app/characters/page.tsx`.
- camelCase for locals and state: `isLoading`, `searchTerm`, `pendingChanges`.
- Boolean state uses `is`, `has`, or `should` prefixes: `isVisible`, `isEditMode`, `hasMigratedOldNotes` (`components/character/notes-tab.tsx`), `isSaving`.
- Module constants use UPPER_SNAKE_CASE for shared lookup tables: `VITALITY_LEVELS` (`components/character/quick-actions-bar.tsx` imports it from `lib/constants/character.ts`).
- Domain keys are Portuguese and must be used as-is: vitality levels `notavel`, `ferido`, `gravementeFerido`, `condenado`, `incapacitado`, `coma`; attribute keys such as `agilidade`, `carisma`. Do not translate these keys into English, because they are persisted as JSON keys in Postgres (see `prisma/schema.prisma`).
- Props interfaces are named `<Component>Props`: `QuickActionsBarProps` in `components/character/quick-actions-bar.tsx`.
- Shared tab props use `CharacterTabProps` from `components/character/types.ts`; `NotesTabProps extends CharacterTabProps {}` in `components/character/notes-tab.tsx`.
- Store state is `<Name>State` (`CharacterState` in `lib/store/character.ts`).
- Zod schemas are camelCase and end in `Schema`: `createCharacterSchema`, `getCharactersQuerySchema`, `characterFullSchema`. Response schemas end in `ResponseSchema` (`getCharacterResponseSchema`), request types end in `Request` (`CreateCharacterRequest`, `LevelUpRequest`), and both are inferred with `z.infer`.
- Types are inferred from Zod schemas rather than duplicated by hand. Use `z.infer<typeof schema>` when adding a new shape.

## Error Handling

- Every handler wraps its body in `try { ... } catch (error) { ... }`.
- On failure, log with `console.error('<Action> <entity>:', error)` and return a JSON error with a status code: `return c.json({ error: 'Failed to fetch characters' }, 500)`.
- Missing records return 404 with a Portuguese or English `error` message: `return c.json({ error: 'Character not found' }, 404)`.
- Input validation uses `zValidator` from `@hono/zod-validator` with a Zod schema on `query`, `param`, or `json` (`zValidator('json', createCharacterSchema)`). Read validated data through `c.req.valid(...)`.
- Responses are checked with `getCharacterResponseSchema.parse({ character })` before returning, so the response shape is validated server-side.
- Every fetch wrapper checks `response.ok` and throws an `Error` with a fixed message. For 404 on a single record, it throws `new Error('Character not found')`.
- Mutations parse the error body and rethrow: `const error = await response.json(); throw new Error(error.error || 'Failed to ...')`.
- These error-parsing lines carry a `// @ts-ignore` comment above the `throw` because `response.json()` is typed as `unknown` in the Hono client. Prefer a typed cast (`(error as { error?: string }).error`) over adding more `@ts-ignore` lines.
- Query invalidation runs in `onSuccess`: `queryClient.invalidateQueries({ queryKey: ['characters'] })`. Single-record updates use `queryClient.setQueryData(['character', variables.id], data)` first.
- User-facing failures use `sonner` toasts: `toast.success('Personagem "..." deletado com sucesso!')` and `toast.error('Erro ao deletar personagem')`, with `try { await mutation.mutateAsync(id) } catch { toast.error(...) }`.
- Some `catch (error)` blocks swallow the error after updating UI state (`components/character/basic-info-tab.tsx`). Log or surface the error when adding new code.
- Async actions set `isSaving: true, error: null` before work, and in `catch` set `error: error instanceof Error ? error.message : 'Erro ao salvar'` and `isSaving: false`.
- Store actions that are placeholders carry the comment `// Aqui integraremos com as APIs de update` and simulate latency with `setTimeout`. Do not copy this pattern for real persistence; use the React Query mutation hooks in `lib/api/queries.ts`.
- Do not return `null` or `[]` silently on errors in API routes. Return a status code and an `error` field.
- Do not add new `@ts-ignore` directives. The codebase has about 10 such lines, all in `lib/api/queries.ts`.

## Logging

- Server-side errors in API handlers use `console.error('Error <action>:', error)`, for example `console.error('Error fetching characters:', error)` in `app/api/[[...route]]/characters/index.ts`.
- The codebase has about 43 `console.` calls across TS/TSX files (excluding `components/ui/`). Many are debugging leftovers. Do not add new `console.log` calls in committed code; use `console.error` only for real error paths.
- Client-side feedback goes to `toast` from `sonner`, not to `console`.

## Function Design

- Hooks and handlers are short wrappers around `fetch` or `api.characters...` calls. Keep them under about 30 lines.
- Large components exist and are a known pattern, not a target. `components/character/basic-info-tab.tsx` (1057 lines), `components/character/notes-tab.tsx` (794 lines), and `components/character/spells-talents-tab.tsx` (545 lines) contain multiple inline sub-components and handlers. When adding behavior, extract helpers into `lib/calculations/` or `lib/constants/` rather than growing these files.
- Components take a single props object with a typed interface (`QuickActionsBar({ character, onNavigate, ... }: QuickActionsBarProps)`).
- Mutation hooks take a single object for multi-part payloads: `useUpdateCharacter` expects `{ id, data }`, and `useCalculateVitality` expects `{ id, data }`.
- Calculation helpers take positional primitives: `calculateVitality(race, class, level)` in `lib/constants/character.ts`.
- Prefer destructuring in the parameter list for components and hooks (`{ level, attributes, vitality, skills, maxBerkana, berkanaBonus }`).
- Hooks return the React Query result object directly (`useQuery` / `useMutation`), so callers use `data`, `isLoading`, `error`, and `mutateAsync`.
- Calculation helpers return plain objects keyed by the Portuguese vitality or attribute keys: `calculateAllAttributes` returns `Record<string, number>`.
- API handlers return `c.json(...)` with a status code on error paths.

## Module Design

- Named exports are the default for components, hooks, schemas, and helpers: `export function Button`, `export const useCharacters`, `export const createCharacterSchema`.
- Page routes are the exception and must use `export default` (required by Next.js App Router): `app/characters/page.tsx`, `app/create/page.tsx`.
- Route-level types are derived from the Hono app and exported as `AppType` from `app/api/[[...route]]/route.ts`. Import that type in `lib/api/client.ts` rather than redefining endpoints.
- Used for `components/character/index.ts` (re-exports tabs, modals, and `QuickActionsBar`) and `lib/calculations/index.ts` as the main module. Import from the barrel: `import { BasicInfoTab, NotesTab } from '@/components/character'`.
- Do not add barrel files for `components/ui/`. Import each primitive directly: `import { Button } from '@/components/ui/button'`.

## Client and Server Boundaries

- Mark client components with `"use client"` at the top of the file. Five TSX files currently do so, including `app/characters/page.tsx` and `providers/query-provider.tsx`.
- Data-fetching hooks in `lib/api/queries.ts` run on the client and are used only from `"use client"` components.
- The Prisma client in `lib/db/index.ts` is server-only. Do not import it from client components.
- Store state in `lib/store/character.ts` is client-only (`zustand` with `devtools`).

## State Management

- Server data: TanStack Query (`@tanstack/react-query`). The `QueryClient` is created in `providers/query-provider.tsx` with `staleTime: 60_000` and `retry: false`. Use query keys `['characters', params]` and `['character', id]`, and invalidate `['characters']` after mutations.
- Editing state: Zustand (`lib/store/character.ts`). Edit flows set `editingField`, `pendingChanges`, and `isSaving`.
- Forms: `react-hook-form` with `@hookform/resolvers` and Zod schemas. Use the shadcn `Form` components from `components/ui/form.tsx`.

- Use `class-variance-authority` (`cva`) for component variants, following `components/ui/button.tsx`.

## Data Shapes and Validation

- Validate all API input with Zod schemas in `lib/schemas/character.ts` and `lib/schemas/calculations.ts`. Add new request shapes there and reference them from the Hono route with `zValidator`.

## Anti-Patterns to Avoid

- Do not add placeholder `setTimeout` persistence in new store actions. Use the React Query mutation hooks.
- Do not add new `@ts-ignore`. Type the error body instead.
- Do not introduce `any` into new function signatures. The codebase has about 33 `any` occurrences (for example `character: any` in `components/character/types.ts` and `components/character/quick-actions-bar.tsx`). Prefer `CharacterFull` from `lib/schemas/character.ts`.
- Do not translate persisted JSON keys or Prisma field names.

## Pattern Overview

- Full-stack monolith deployed as one Vercel project (`vercel.json`, function `app/api/[[...route]]/route.ts`, `maxDuration: 30`, region `gru1`).
- Client pages fetch everything over HTTP; there are no server components that query the database. Pages are all `"use client"`.
- End-to-end types: `AppType` exported from `app/api/[[...route]]/route.ts` is consumed by `hc<AppType>` in `lib/api/client.ts`, so the client is typed from the server routes.
- Zod is the single source for validation (`zValidator` on the server, `z.infer` types on the client).
- Character data is stored largely as untyped JSON columns (`attributes`, `vitality`, `skills`, `weapons`, `spells`, `talents`, etc.); shape is enforced in zod, not in the DB.
- UI is in Portuguese (pt-BR); user-facing strings and code comments are Portuguese.

## Key Abstractions

- Purpose: Share route types between server and client without codegen
- Examples: `app/api/[[...route]]/route.ts` (`export type AppType`), `lib/api/client.ts`
- Pattern: Chained `.get/.post/.put/.delete` on a Hono instance with `zValidator` middleware
- Purpose: Request validation, response shaping, and TypeScript types from one definition
- Examples: `lib/schemas/character.ts` (`createCharacterSchema`, `updateCharacterSchema`, `characterFullSchema`), `lib/schemas/calculations.ts` (`calculateVitalityRequestSchema`, `calculateVitalityResponseSchema`, ...)
- Pattern: `export const xSchema = z.object(...)` then `export type X = z.infer<typeof xSchema>`
- Purpose: Game rules (attribute totals, vitality tiers, berkana, skill points, XP curve)
- Examples: `lib/calculations/index.ts`, `lib/constants/character.ts` (`calculateXPForNextLevel`, `calculateBerkana`, `calculateVitality`)
- Pattern: Plain exported functions taking primitives or records and returning numbers or objects. Two parallel sets exist (see Anti-Patterns).
- Purpose: Avoid multiple `PrismaClient` instances under Next dev hot reload
- Examples: `lib/db/index.ts`
- Pattern: `globalThis.prisma` cache when `NODE_ENV !== 'production'`
- Purpose: Each sheet tab is a self-contained component taking `CharacterTabProps`
- Examples: `components/character/basic-info-tab.tsx`, `components/character/skills-kit-tab.tsx`, `components/character/spells-talents-tab.tsx`, `components/character/notes-tab.tsx`
- Pattern: Barrel export in `components/character/index.ts`; props `character`, `characterId`, `isEditMode`, plus modal open state

## Architectural Constraints

- **Threading:** Single-threaded Node/edge request handling via Next.js and Vercel functions. No worker threads. Client UI runs on the browser main thread.
- **Global state:** `lib/db/index.ts` caches `PrismaClient` on `globalThis` in non-production. `providers/query-provider.tsx` keeps a module-level `browserQueryClient`. `lib/store/character.ts` is a module-level Zustand store singleton.
- **Circular imports:** None observed. The only server-to-client type dependency is `lib/api/client.ts` importing the type `AppType` from `app/api/[[...route]]/route.ts`, which is type-only and does not create a runtime cycle.
- **Runtime boundary:** Client code must never import `lib/db` or `lib/generated/prisma`. Only `app/api/[[...route]]/characters/index.ts` does.
- **Generated code:** `lib/generated/prisma` is produced by `prisma generate` (run by `postinstall` and `build` in `package.json`). It is gitignored; do not edit it.
- **Deployment window:** The API function has `maxDuration: 30` in `vercel.json`.

## Error Handling

- Route-level `try/catch` in `app/api/[[...route]]/characters/index.ts`, with Portuguese error messages
- Client hooks in `lib/api/queries.ts` throw `Error` objects from `response.json().error`, and components show them with `sonner` toasts
- Pages render an error card when `useCharacter` returns an error (`app/character/[id]/page.tsx`)
